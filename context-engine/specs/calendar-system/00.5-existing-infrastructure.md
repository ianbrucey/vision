## 1. Critical Discovery: Naming Collision with `events`

**⚠️ The `events` table already exists at `schemas/001_core.sql:319`.**

This table stores **historical case timeline events** — facts that happened in the real world (findings, decisions, communications). It has a fundamentally different purpose from calendar events (future scheduled items).

| Dimension | Existing `events` | New `calendar_events` |
|-----------|------------------|----------------------|
| **Temporal** | Past — what happened | Future — what's scheduled |
| **Columns** | `event_at`, `event_date`, `kind`, `actor`, `summary` | `start_time`, `end_time`, `title`, `description`, `category` |
| **Domain** | Case timeline facts | Calendar scheduling |
| **FKs** | `case_id`, `actor_id → parties`, `workspace_id` | `case_id`, `workspace_id → workspaces`, `created_by` TEXT CHECK (user/agent) |

**Verdict:** New tables MUST be named `calendar_events` and `reminders` to avoid collision. No alteration to existing `events` table.

### 2.1 Tables to Reference (Pattern Sources)

| Table | Location | Relevant Patterns |
|-------|----------|-------------------|
| `tasks` | `001_core.sql:551-567` | Case-scoped item with `title`, `notes`, `deadline`, `status`, `priority`, `created_by` FK, `CHECK` constraints, dedicated indexes |
| `task_documents` | `001_core.sql:574-579` | Junction table pattern for attaching documents to items |
| `events` | `001_core.sql:319-343` | Case-scoped, `event_at` TIMESTAMPTZ, `event_date` DATE, JSONB `metadata` — but DO NOT reuse this table |
| `cases` | `001_core.sql:49-83` | Parent FK target |
| `users` | `001_core.sql:410-426` | `created_by` FK target (UUID) |

### 2.2 Patterns to Copy

**From `tasks`:**
- `case_id INTEGER REFERENCES cases(id) ON DELETE CASCADE NOT NULL` — always cascade
- `CHECK (status IN (...))` — enumerated statuses
- `CHECK (priority IN (...))` — enumerated categories (rename to `category`)
- `created_by TEXT NOT NULL DEFAULT 'user' CHECK (created_by IN ('user', 'agent'))` — follows `drafts`/`business_vault` pattern
- `metadata JSONB DEFAULT '{}'` — extensibility escape hatch
- `created_at / updated_at TIMESTAMPTZ DEFAULT now()`
- Indexes: `(case_id)`, `(case_id, deadline)`, `(case_id, status)`

**From `events`:**
- `TIMESTAMPTZ` for date/time columns (not `DATE` — calendar events need time)
- `event_date DATE` for date-only queries (all-day events)

### 4.5 Styling Strategy

React Big Calendar ships its own CSS. Two approaches:

**Approach A (Recommended):** Import RBC CSS into a scoped wrapper, then override with Tailwind tokens via a `calendar-overrides.css` file loaded after. The override maps:
- `.rbc-toolbar` → flex with surface-1 bg
- `.rbc-header` → text-sm font-medium, surface-2 bg
- `.rbc-event` → brand bg, rounded-lg
- `.rbc-today` → brand-bg (subtle)
- `.rbc-off-range-bg` → surface-0
- `.rbc-btn-group button` → match secondary button pattern

**Approach B:** Don't import RBC CSS at all; write full custom styles. More control, more work.

Verdict deferred to State 4 (Execution) — the Builder decides based on how invasive the overrides need to be.

## 5. Agent Tools: Integration Points

### 5.1 Pattern to Follow

Agent tools are registered inside `create_vision_server()` in [`backend/chat/tools.py`](backend/chat/tools.py:120). The pattern is:
1. `case_id` is captured in closure — the agent never provides it
2. Each tool is an `async def` with `args: dict[str, Any]` parameter
3. Database functions imported lazily (`from core.db import ...` inside the function)
4. `_conn()` provides a database connection
5. Return `_result({...})` on success, `_error(f"...")` on failure
6. Schema helpers: `_doc_in_case()`, `_block_in_case()`, `_strategy_in_case()` verify FK ownership
7. Tool annotations: `annotations=ToolAnnotations(readOnlyHint=True)` for read-only tools

### 5.2 Tools to Register (NET NEW)

| Tool Name | Type | Input Schema | Pattern Source |
|-----------|------|-------------|---------------|
| `create_calendar_event` | Write | `{title, description?, start_time, end_time?, all_day?, category?, location?}` | `create_task` |
| `list_calendar_events` | Read | `{start_date?, end_date?, category?, limit?}` | `list_tasks` |
| `get_calendar_event` | Read | `{event_id}` | `get_task` |
| `create_reminder` | Write | `{title, description?, remind_at, category?, event_id?}` | `create_task` |
| `list_reminders` | Read | `{status?, category?, limit?}` | `list_tasks` |
| `get_reminder` | Read | `{reminder_id}` | `get_task` |

## 8. Risk Register: Conflicts and Constraints

### 8.1 Conflicts Found

| # | Conflict | Severity | Mitigation |
|---|----------|----------|------------|
| 1 | **`events` table exists** — cannot name calendar table `events` | **HIGH** | Name it `calendar_events`. Already factored into Brief and this document. |
| 2 | **Tab limit approaching** — 7 tabs, mobile shows 4 primary + 3 secondary under "More" | **LOW** | Design system supports this. Calendar goes under "More" unless user demotes an existing primary tab. |
| 3 | **RBC CSS bleed** — React Big Calendar's stylesheet may conflict with Tailwind tokens | **MEDIUM** | Scoped override strategy. Evaluate approach A vs B during execution. |
| 4 | **`date-fns` peer dep** — React Big Calendar v1.x historically depended on `moment`. v1.8+ supports `date-fns`. | **LOW** | Pin to `react-big-calendar@^1.8` with `date-fns@^3` as the date math library. Verify before install. |

### 8.2 Constraints (Non-Negotiable)

- [x] Must use existing `cases` table FK — no new case concept
- [x] Must follow existing API route pattern (FastAPI router + Pydantic + `Depends(get_current_user)`)
- [x] Must follow existing agent tool closure pattern in `create_vision_server()`
- [x] Must follow "Command" design system — no new colors, fonts, spacing values
- [x] Must support mobile-first: 320px viewport, 44px touch targets, bottom tab bar safe area
- [x] Must not break existing tabs or their state when navigating to/from Calendar
- [x] Polling cadence must not overload the API (30s interval, checked against existing 5s job polling)
- [x] `created_by` uses TEXT CHECK pattern (`'user'` or `'agent'`) matching `drafts` and `business_vault`

### 8.3 Open Questions (Resolved During Execution)

- Does Calendar get a primary tab slot, or stay under "More"? → UI spec phase decision
- Does RBC v1.8+ with date-fns v3 work cleanly with our build? → Verify during `npm install`
- How many CSS overrides are needed for RBC to match "Command"? → Discover during implementation
- Should calendar events support document attachment (like tasks do)? → Not in v1 scope, but schema could support it via junction table

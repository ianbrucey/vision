# T1.2 — Admin Settings Page

**Status:** pending
**Depends on:** T1.1

---

## Goal

Admin sees a Settings/Users page at `/settings` to manage user accounts. Hidden from non-admin users.

## UI

```
┌─────────────────────────────────────────────────┐
│ Settings                                [Add User] │
│─────────────────────────────────────────────────│
│ Username    Email              Role    Active    │
│─────────────────────────────────────────────────│
│ admin       —                  admin   ●  [Edit] │
│ ianbruce    ian@justicequest.. user    ●  [Edit] │
│ newhire     new@test.com       user    ○  [Edit] │
│ ...                                             │
└─────────────────────────────────────────────────┘
```

- **Add User button** → modal: username, email, password, role dropdown (user/admin)
- **Edit button** → inline row becomes editable: email, role dropdown, active toggle
- **Active toggle** → green dot = active, gray dot = disabled (soft-disable, reversible)
- **Role** displayed as badge: admin = red, user = gray

## Acceptance Criteria

- [ ] Admin navigates to `/settings` → sees user table
- [ ] "Add User" modal creates a user, table refreshes
- [ ] Edit mode: can change email, role, toggle active status
- [ ] Disabling a user → `is_active = false` → they can't log in (backend enforces)
- [ ] Re-enabling a user → `is_active = true` → they can log in again
- [ ] Non-admin users: Settings link not in nav, 403 page if they navigate directly
- [ ] Password field in "Add User" is masked, minimum 6 characters
